Explain Codd's law for RDBMS.

3
A4 PagesRules 0–4 · rules 5–12 · meaning
Page 1 of 3Question 5 · Codd and rules 0–4

Codd's Twelve Rules

Dr. E. F. Codd proposed the relational model in 1970. In 1985 he published thirteen rules — usually called Codd's twelve rules, because numbering starts at zero — as a test of whether a database product is truly relational. A system that follows them stores data in tables only, and the user never needs to know how the bytes are arranged.

RuleNameWhat it demands
0FoundationThe system must qualify as relational, as a database and as a DBMS
1InformationAll data is stored as values in tables — nothing else
2Guaranteed accessEvery value is reachable by table name, primary key and column name
3Systematic nullsA null means "unknown", not zero or blank, and is handled consistently
4Dynamic catalogThe description of the database is itself stored in tables and can be queried
Page 2 of 3Question 5 · Rules 5–12

The Remaining Rules

Rules 5 to 12 protect the user from the physical details of storage and from any back door that would let a program bypass the relational model.

RuleNameWhat it demands
5Comprehensive sublanguageOne language (SQL) must handle definition, query, update and security
6View updatingViews can be updated where the change maps back to base tables
7High-level insert, update, deleteOperations work on whole sets of rows, not one record at a time
8Physical data independenceChanging files, indexes or disks must not change the application
9Logical data independenceAdding a column or splitting a table must not break existing queries
10Integrity independenceConstraints are stored in the catalog and checked by the DBMS
11Distribution independenceData may be spread over several locations without changing SQL
12Non-subversionNo low-level tool may bypass the rules of the relational model

Rules 8, 9 and 11 are the most valuable in practice: they are what allow a DBA to add an index in the morning and have the evening reports run faster, without any programmer touching a line of code.

  APPLICATION  ── logical view ──▶  views, tables, constraints
                                         │  logical independence (rule 9)
                                         ▼
  STORAGE     ── physical view ─▶  files, indexes, tablespaces
                                         │  physical independence (rule 8)
                                         ▼
  LOCATION    ── distribution ──▶  server A + server B
                                            distribution independence (rule 11)
Page 3 of 3Question 5 · Why the rules matter

Meaning and Use in Oracle

Codd's rules are a checklist, not a law of physics. Oracle, SQL Server, PostgreSQL and MySQL satisfy most of them, and each one shows up as a familiar feature:

Rule 4 is the data dictionary — USER_TABLES and USER_CONSTRAINTS describe the system. Rule 6 is CREATE VIEW. Rule 10 is PRIMARY KEY, CHECK and FOREIGN KEY constraints.

codd_oracle.sql
-- Rule 1, 2 & 10: Table storage, primary key access & declarative integrity
CREATE TABLE student (
    roll_no NUMBER PRIMARY KEY,              -- Rule 2: unique key access
    name    VARCHAR2(50) NOT NULL,
    marks   NUMBER CHECK (marks >= 0)        -- Rule 10: catalog integrity
);
-- Rule 3 & 4: Systematic NULL query & active dynamic catalog inspection
SELECT name FROM student WHERE marks IS NULL; -- Rule 3: 3-valued logic
SELECT table_name FROM user_tables;          -- Rule 4: queryable dictionary

The rules also explain why the model is trusted. Because every value sits in a known cell of a known table, any row can be found without scanning a file by hand. Because constraints live in the catalog, the same rule protects every program. Because rows have no fixed order, the optimiser is free to read them in the cheapest way.

ViolationWhy it breaks the model
Storing a list in one columnRepeating groups make a value unreachable by key
Hiding data in files outside the catalogRule 1 and rule 4 both fail
Letting a program read the data file directlyRule 12 (non-subversion) fails
Using blank instead of nullRule 3 fails — "unknown" becomes "empty"

Conclusion

Codd's twelve rules (thirteen with rule 0) describe a database in which all data is tabular, reachable by key, described by its own catalog, queried by one language, and independent of storage, structure and location.

Page 1 of 3Question 6 · Inner joins

What a Join Does

A join combines rows from two or more tables using a related column. The database first forms the Cartesian product — every row of the first table paired with every row of the second — and then keeps only the pairs that satisfy the join condition. Without that condition the product is meaningless and grows very fast.

Our example uses two small tables. EMP stores empno, name and deptno; DEPT stores deptno and dname. Note that Neha has no department, and Admin has no employee.

  EMP                          DEPT
  ┌───────┬────────┬────────┐  ┌────────┬────────┐
  │ empno │ name   │ deptno │  │ deptno │ dname  │
  ├───────┼────────┼────────┤  ├────────┼────────┤
  │  101  │ Rahul  │   10   │  │   10   │ Sales  │
  │  102  │ Aman   │   20   │  │   20   │ HR     │
  │  103  │ Neha   │  NULL  │  │   30   │ Admin  │
  └───────┴────────┴────────┘  └────────┴────────┘
        join condition:  EMP.deptno = DEPT.deptno

Equi join and natural join

An equi join compares columns with =; a natural join does the same automatically on every column that has the same name, and prints the shared column once. A theta join uses any other comparison, such as < or BETWEEN.

inner_join.sql
SELECT e.name, d.dname
FROM   emp e INNER JOIN dept d
ON     e.deptno = d.deptno;

-- natural join writes the same thing without the condition
SELECT name, dname FROM emp NATURAL JOIN dept;

The inner join returns only Rahul–Sales and Aman–HR. Neha and Admin disappear because they have no matching value.

Page 2 of 3Question 6 · Outer, self and cross joins

Outer Joins

An outer join keeps the unmatched rows and fills the missing side with NULL. This is how a report shows "every employee, with a department if one exists".

JoinKeepsRows in our example
LEFT OUTER JOINAll left rows + matchesRahul-Sales, Aman-HR, Neha-NULL
RIGHT OUTER JOINAll right rows + matchesRahul-Sales, Aman-HR, NULL-Admin
FULL OUTER JOINAll rows from both sidesAll five combinations
outer_join.sql
SELECT e.name, d.dname
FROM   emp e LEFT OUTER JOIN dept d
ON     e.deptno = d.deptno;

SELECT e.name, d.dname
FROM   emp e FULL OUTER JOIN dept d
ON     e.deptno = d.deptno;

Self join and cross join

A self join joins a table to itself, which is how a manager column is resolved: the same EMP table appears twice, once as employee and once as manager. A cross join deliberately returns the full Cartesian product and is used for combinations such as every size with every colour.

self_cross.sql
SELECT e.name AS employee, m.name AS manager
FROM   emp e LEFT JOIN emp m ON e.mgr = m.empno;

SELECT e.name, d.dname FROM emp e CROSS JOIN dept d;
-- 3 employees x 3 departments = 9 rows
Page 3 of 3Question 6 · Visual summary

The Four Common Joins at a Glance

Choosing the Right Join

NeedUse
Only matched recordsINNER JOIN
All records of the main table, matched or notLEFT OUTER JOIN
All records of the lookup tableRIGHT OUTER JOIN
Every record from both sidesFULL OUTER JOIN
Hierarchy within one tableSELF JOIN
Every combinationCROSS JOIN

A join is written in the FROM clause and its condition in ON; a filter on the result belongs in WHERE. Putting a filter on the outer-joined table inside WHERE silently turns a LEFT join back into an INNER join — a very common exam and interview trap.

Conclusion

A join pairs rows of two tables through a related column. INNER keeps matches, LEFT/RIGHT/FULL keep unmatched rows with NULLs, SELF joins a table to itself and CROSS returns every combination.

The E-Learning Model

An ER (Entity–Relationship) diagram shows the things a system stores and how those things relate. An entity becomes a table, an attribute becomes a column, a relationship becomes a foreign key, and cardinality (1:1, 1:N, M:N) decides where that key is placed.

Our e-learning system needs six entities. STUDENT (student_id, name, email) is the learner. TEACHER (teacher_id, name, department) creates the course. COURSE (course_id, title, credits) is the subject offered. MODULE (module_id, title, duration) is one unit inside a course. ENROLLMENT (enroll_id, date, grade) records that a student joined a course. ASSESSMENT (assessment_id, type, max_marks) is a quiz or assignment inside the course.

EntityPrimary keyImportant attributes
STUDENTstudent_idname, email, phone
TEACHERteacher_idname, department
COURSEcourse_idtitle, credits, teacher_id
MODULEmodule_idtitle, duration, course_id
ENROLLMENTenroll_iddate, grade, student_id, course_id
ASSESSMENTassessment_idtype, max_marks, course_id

ENROLLMENT exists only because a student and a course have an M:N relationship. A relational table cannot hold a list of courses inside a student row, so the pair is stored once per enrolment — a bridge (associative) entity.

Mapping the Diagram to Tables

Each entity becomes a table with its primary key. Each 1:N relationship is implemented by copying the parent key into the child table as a foreign key. The M:N relationship between STUDENT and COURSE becomes the ENROLLMENT table, whose primary key is its own id and whose two foreign keys point at the two parents.

TablePrimary keyForeign key(s)
teacherteacher_id—
coursecourse_idteacher_id → teacher
modulemodule_idcourse_id → course
studentstudent_id—
enrollmentenroll_idstudent_id → student, course_id → course
assessmentassessment_idcourse_id → course

A useful query follows the diagram directly: list every student with the courses they joined. It starts at STUDENT, passes through ENROLLMENT and ends at COURSE — the same path the diagram draws.

e_learning.sql
SELECT s.name, c.title, e.grade
FROM   student s
JOIN   enrollment e ON e.student_id = s.student_id
JOIN   course c     ON c.course_id  = e.course_id
ORDER BY s.name, c.title;

Two rules keep the model correct. Every foreign key must point at an existing primary key (referential integrity), and a student must not be enrolled twice in the same course — enforced with a UNIQUE (student_id, course_id) constraint on ENROLLMENT.

Conclusion

The e-learning ER model has six entities: student, teacher, course, module, enrollment and assessment. The M:N link between student and course is resolved by ENROLLMENT, and every 1:N link becomes a foreign key on the many side.
