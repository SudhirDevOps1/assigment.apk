Question Three · Distributed Components

Explain scalability of DCOM.

3
A4 PagesConcept · mechanisms · limits
Page 1 of 3Question 3 · What scalability means

Scalability in a Distributed System

Scalability is the ability of a system to handle a growing amount of work — more users, more requests, more data — by adding resources, without rewriting the software and without a proportional fall in response time. A system that serves 200 users well and 400 users badly is not scalable.

DCOM (Distributed Component Object Model) is Microsoft's extension of COM across machine boundaries. The client holds a proxy, the server hosts a stub, and RPC carries the marshalled call over the network. Because a component can run on any machine, capacity can be added by moving components to another server — this is exactly what makes DCOM scalable.

Capacity is added in one of three ways: scale up (a bigger machine), scale out (more machines behind a balancer) or partition (split the work by business area, so each server owns its own objects).

Page 2 of 3Question 3 · What DCOM provides

Mechanisms that Make DCOM Scalable

Location transparency. The client asks for a CLSID or ProgID; the Service Control Manager starts or finds the object and returns a proxy. The same code therefore runs in-process today and on a second server tomorrow.

Apartment threading. Objects declare a threading model. Single-threaded apartments (STA) serialise calls, while the multithreaded apartment (MTA) lets the runtime use a thread pool, so extra CPU cores are actually used.

Object pooling and JIT activation (COM+). Instead of creating an object for every request, the server keeps a pool of ready instances; just-in-time activation builds an instance only for the length of the call and then releases it.

Stateless design. If the object keeps no private user state — the state lives in a database — then any server can answer the next call. This single decision makes load balancing possible.

Asynchronous and queued calls. With COM+ Queued Components the client posts the request to MSMQ and returns at once; the server drains the queue at its own speed, so a traffic spike becomes a longer queue instead of a timeout.

Page 3 of 3Question 3 · Limits and tuning

What Limits DCOM Scalability

Chatty interfaces. Every remote call is a network round trip. An object that reads one field at a time forces hundreds of trips; a chunky interface that returns a whole record in one call does the same work in one trip.

Marshalling and security overhead. Arguments must be packed, and if packet privacy is switched on they are also encrypted and decrypted on every call. Reusing a session and keeping calls few and large is faster than many small secure calls.

Shared state and locking. A single MTA lock or a database row lock turns extra servers into a queue. Partitioning the data removes the contention.

No built-in clustering. DCOM itself does not balance or fail over. In practice it is combined with Network Load Balancing, COM+ Application Center routing, or Windows failover clustering.

  CHATTY  (poor scaling)                CHUNKY  (good scaling)
  client ──▶ getName()                   client ──▶ getRecord(101)
         ◀── "Rahul"                                    ◀── {id, name, marks}
  client ──▶ getMarks()                  ── 1 round trip ──
         ◀── 480
  client ──▶ getCity()     3 round trips, 3 marshals
         ◀── "Ara"

A 1,000-user result system scales like this: make the result object stateless, pool it, put the database behind it, batch the marks lookup, and place a second server behind a balancer. Each step adds capacity without changing a line of client code — that is the real meaning of DCOM scalability.

Conclusion

DCOM scales because location is transparent: objects can be pooled, made stateless and spread across servers. The network is the limit, so coarse interfaces, short sessions and partitioned data decide how far the system grows.

Page 1 of 3Question 4 · Security goals

Why COM and DCOM Need Security

COM objects inside one process are protected by the operating system's own boundary. DCOM sends the same calls across a network, where an attacker can eavesdrop, spoof a client, alter a message, replay an old request or simply activate a component that should never have started. Security therefore becomes part of the design, not an add-on.

Five goals are protected: authentication (who is calling), authorisation (may they call it), integrity (the bytes were not changed), confidentiality (nobody can read them) and auditing (the attempt is recorded).

DCOM does not invent cryptography. It delegates to SSPI and the RPC security provider, which use Kerberos in a domain or NTLM where Kerberos is unavailable. The level of protection is chosen per call through the authentication level.

Page 2 of 3Question 4 · Authentication and impersonation

Authentication Levels

The client states how strongly it wants each call protected. The six RPC authentication levels form a ladder, and each rung costs more CPU than the one below it.

Impersonation decides what the server may do with the client's identity. Anonymous hides the caller. Identify only lets the server check the name. Impersonate lets the server act as the client on the same machine. Delegate lets it act as the client on another machine too, and works only with Kerberos.

Authorisation and Configuration

Authentication says who; authorisation says whether. Two access-control lists protect every DCOM server: launch permissions decide who may start the server, and access permissions decide who may connect to a running object. Both are stored as security descriptors with a DACL and are edited with dcomcnfg (Component Services) or by code.

Inside the server, CoInitializeSecurity sets the process-wide default, while CoSetProxyBlanket on the client adjusts the level for one interface. Per-interface security therefore lets a public read method stay open while a sensitive method demands packet privacy.

  CLIENT                        SCM                    SERVER
    │  1. CoCreateInstance        │                       │
    ├───────────────────────────▶ │ 2. check LAUNCH ACL   │
    │                             ├─────────────────────▶ │ 3. start
    │  4. bind (auth level)       │                       │
    ├───────────────────────────▶ │ 5. check ACCESS ACL   │
    │                             │                       │ 6. token checked
    │  7. method call ──────────────────────────────────▶ │    by server
    │ ◀──────────────────────────────── return + signature │
    Key: authentication happens at step 4, authorisation at 5 and 6

Best practice. Never ship a server with authentication level NONE; prefer PKT_INTEGRITY or PKT_PRIVACY. Grant launch rights to a role, not to Everyone. Keep delegation switched off unless a three-tier design truly needs it. Restrict DCOM at the firewall, and remember that a stale registry ACL can silently undo every setting made in the user interface.

Conclusion

DCOM security is a chain: SSPI proves identity, the authentication level protects each packet, impersonation limits what the server may do, and the launch and access ACLs decide who gets that far. The weakest link sets the real strength.
